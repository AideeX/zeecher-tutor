# Privacy and safety implementation notes

Both learners are under 13. This implementation sends no child content to a model. The external AI endpoint is blocked server-side, with an explicit disabled-by-default `UNDER13_AI_ENABLED` setting; even enabling the setting returns an unavailable response until a compliant provider is implemented. No API key is required or stored.

The supplied build prompt identifies appropriate OpenAI ZDR arrangements and relevant legal obligations as prerequisites to child-to-model processing. The official under-18 guidance was retrieved and inspected on 23 October 2026 after network access was restored. It explicitly requires appropriate API zero data retention before processing personal data of children under 13 or the applicable age of consent. This family has no verified ZDR arrangement or child-to-model launch approval. No legal or compliance certification is claimed. A future provider needs current policy review, documented approvals/technical controls, minimisation, quota enforcement, moderation and independent testing before any child input is transmitted.

Parent passwords use salted scrypt; session tokens are random and stored as hashes. Cookies are HttpOnly/SameSite Strict, have limited lifetimes, and can be Secure for HTTPS. Parent-only routes check ownership on the server. Child sessions are scoped to one learner. Launching a child revokes the current parent token. State/export responses are no-store. Mutations require the matching application Origin; JSON schemas and size limits apply. Persistent rate limits cover authentication, question submission, lesson starts, help and writing. No password recovery, email or public sign-up system is provided.

Only nicknames are requested for children. No birthdate, school, address, photo or email is needed. Original numeric/choice responses and explicitly saved writing revisions are stored locally; unsaved reasoning notes remain in component state. Exports include free-text writing and must be reviewed before sharing. The local writing checklist cannot assess semantic accuracy or certify mastery.

Learner record deletion removes attempts, assistance events, sessions, schedules and writing, and revokes child access. It retains the two profiles/settings, plus a minimal parent audit of the action. SQLite secure_delete is enabled; deletion is not a guarantee of forensic removal from storage media, WAL snapshots or backups. Operators must manage disk encryption and backup retention. A full family-account deletion flow also removes both profiles and parent authentication records.

The application database is not encrypted. Its directory is private, and the database/setup-code files use restrictive permissions. Never publish a snapshot containing actual child data to a shared environment. No actual family records were created in the normal development database during implementation.

Science lessons use safe original examples. The private source's tongue-map claim is excluded and recorded as a factual conflict. Activities involving heat, sharp objects or directly viewing the Sun are not offered. Household observations ask for adult supervision where relevant. Confusing results should be discussed with a parent/teacher; the assistant does not claim infallibility.

Before public hosting: HTTPS and secure cookies; exact APP_ORIGIN; persistent protected storage; dependency/security review; backup/deletion policy; accessible content review; applicable Nigerian data/privacy assessment; account recovery and operational monitoring. These are deployment requirements, not claims that this local build has already passed an external audit.
